**Four requested UI changes: hide-controls toggle, 3D pinch-to-zoom, Model legend moved to a horizontal row, title/subtitle hidden**
- Planned directly, then executed as four independent pieces:
- **Hide-controls toggle**: new `#controls-toggle-btn` in its own row above `.controls` (Launch Site/Date/View/Copy link) -- reported directly, to let mobile users see more of the map without scrolling past that row first. Deliberately its own row OUTSIDE the map, not a map-corner overlay, so it stays reachable in one fixed spot regardless of scroll position or which map view is active. Same chevron-toggle idea `renderWeatherPanel()`'s own `weatherPanelCollapsed` already established for the Weather panel; session-only, not persisted.
- **3D pinch-to-zoom**: reported directly -- 2-finger touch on the 3D canvas only ever panned (translated), never zoomed. The 2D map already had a clean combined pan+pinch-zoom implementation (tracks both touch points, zooms by the ratio of distance-between-fingers while panning by their midpoint's delta, in one gesture); ported the same pattern into `descent3d.js`'s existing 2-finger-pan handling -- fingers spreading apart now zooms in (same direction the mouse wheel already uses), while still panning via the midpoint exactly as before. Desktop right-click-drag pan is unaffected (no pinch-distance concept applies to a single pointer). Verified via synthetic pinch-out gesture: `path3dZoom` went from 1 -> 3.45; mouse-wheel zoom and single-finger orbit-drag re-confirmed unaffected.
- **Model legend moved to a horizontal row below the map**: previously a vertical `.alt-row` stack in the right-hand sidebar (`.side-col`); moved to directly below `.map-view-wrap` and changed to `display:flex; flex-wrap:wrap` with each chip sized to its own content (`flex:0 0 auto`) instead of a full-width block. `buildModelLegend()` needed no JS changes (ID-based lookup, doesn't care where in the DOM `#model-legend` lives). Fits one row at desktop widths by default; on mobile the unavailable-model "(no data)" suffix was wide enough to force a 3rd wrapped row at a real 390px width -- shortened to "(N/A)" (full explanation is still one hover away, unchanged `title` attribute) plus tighter padding/gap under the existing 760px breakpoint, confirmed to land at exactly 2 rows for a 6-model legend.
- **Title/subtitle hidden**: `<h1>`/`#subtitle` set to `display:none` per direction ("not doing anything userful," to be reworked later) -- kept in the DOM rather than removed, since `describeEntry()` (app.js) still writes real content into `#subtitle` on every dataset load.
- Verified in-browser (Playwright): zero console errors across 5 site/mode combinations; model-legend toggle/solo still functions correctly from its new location; hide-controls toggle confirmed both directions with label text in sync; mobile (390px) confirmed 2-row model legend and working toggle.

**Reverted: altitude fly-out's slider-tick-aligned row layout -- broke on mobile**

**Fixed: real bug -- Specific-altitude zones only rendered when they happened to land on a ladder rung**
- Reported directly: "In 2d, the splash zone isn't being rendered unless it's on a 2k' marker. Those should be rendered across altitudes." Root cause: `applyIsolation()`'s byAltitude branch filtered every `.zone-group` against `state.selectedAlts` (the checkbox ladder's own Set) unconditionally -- but when "Specific altitude" is active, `render()` builds exactly one zone-group at whatever arbitrary value the slider was dragged to, which is essentially never itself a member of `selectedAlts` (that Set only ever holds the discrete ladder's own rungs, e.g. 2000/4000/6000/8000/10000). The one real zone-group got hidden every time, unless the drag happened to land exactly on a ladder value by coincidence. `isPointVisible()` (hover-tooltip hit-testing) had the identical bug. Fixed both: `state.customAlt !== null` now bypasses the `selectedAlts` filter entirely (there's only one zone-group to show in that case, unconditionally). Verified directly: `zoneFor()` was already correctly computing real points at arbitrary altitudes (4700ft, 9300ft) the whole time -- confirmed via direct evaluation that the bug was purely the visibility filter, not the simulation; both values now render a real hull on the map; checkbox-ladder toggle/solo/revert re-verified unaffected by the fix.

**Pipeline: T-0 History now shows a frozen pre-launch snapshot, not whichever same-day pull ran last**
- Reported directly, following up on the T-0/HRRR-analysis convergence investigation earlier this session: the T-3..T-0 cron window fires 4x/day for every model (00:15/06:15/12:15/18:15 UTC), and `pull_live_forecast.py`'s `capture_date` is a bare UTC date -- every same-UTC-day run overwrites the same `captured_{capture_date}.parquet`, by design, so a T-0 day's stored forecast has always been whatever happened to run *last* that day (often after launches were already over), not what a launch director actually saw before flying. Framed directly: "I checked this in the morning, then focused on flying. What actually happened compared to what I saw?"
- New `config.MORNING_SNAPSHOT_HOUR_LOCAL = 9`: a T-0 pull (`capture_date == target_date`) that lands before this local hour now also gets frozen into a second file, `captured_{capture_date}_morning.parquet` (`save_capture()`, `pull_live_forecast.py`) -- re-written by every pre-9am pull that day (so the latest of those wins, i.e. the closest point before a typical 9am launch start), untouched by anything after. The original `captured_{capture_date}.parquet` keeps getting overwritten all day exactly as before -- that's what keeps the live/current maps ("as people fly") fresh; nothing about the live view changed.
- `build_points_history()` (`splash_zones.py`): T-0's own row in History (2D and 3D) now reads the frozen `_morning` file when one exists for that target date, instead of the ongoing file -- T-1..T-7 rows are unaffected (only a same-day capture can have this ambiguity at all). Older target dates predating this feature have no `_morning` file and silently keep the prior behavior.
- `is_morning_snapshot` is computed by the caller (`pull_live_forecast.py`'s `__main__`, using real wall-clock local time via `zoneinfo`), not inside `save_capture()` itself -- `backfill_capture()`'s retrospective path (Single Runs API, reconstructing past T-7..T-0 history) has no "did I check before 9am" question to ask, so it's unaffected by default (`is_morning_snapshot=False`).
- Verified directly: `save_capture(is_morning_snapshot=True)` writes both files; the gating condition (`capture_date == target_date and local_hour < 9`) checked across boundary cases (07:15/08:59/09:00/13:15 local, plus a T-1 lead pull) -- all five resolved as expected. End-to-end against a copy of real Hearne 2026-08-08 capture data (isolated scratch dir, real data on disk never touched -- confirmed via `git status` after): wrote a frozen `_morning` copy, then mutated the "ongoing" file's wind speed by +50mph to simulate a later same-day overwrite; `build_points_history()` correctly cached and read `splash_points_captured_2026-08-08_morning.parquet` for T-0, and the computed landing points diverged sharply from what the same code produces reading the mutated ongoing file directly (e.g. one model's T-0 point: (265, 442)ft from the morning snapshot vs. (1876, 3086)ft from the mutated ongoing file) -- confirms the redirect changes real computed output, not just which filename gets touched.

**Fixed: real cache-busting gap for `descent3d.js` in production, plus a local-dev cache-busting gap for everything**
- Reported directly, testing the History+3D fix above against a real local server: a hard refresh (Ctrl+Shift+R) kept serving stale `app.js`, while a fresh incognito window showed the fix -- flagged as a possible risk to real users too, not just a local annoyance.
- Investigated rather than assumed: `pages.yml`'s own "Version app.js/app.css for reliable cache-busting" step (`sed -i "s|assets/js/app.js|assets/js/app.min.js?v=$V|; ..."`) never had a pattern for `assets/js/descent3d.js` at all -- confirmed directly by reading the exact `sed` command, not inferred. That file has existed unversioned AND unminified in production this whole time (`scripts/minify_js.py` only ever processed `app.js`); every deploy since `descent3d.js` was added could leave a backgrounded/bfcache-restored tab running stale 3D code indefinitely, the exact failure mode the `?v=<sha>`/`version.json` mechanism was built to prevent for `app.js`/`app.css` -- it just never got extended to cover the newer file. **Fixed: 3D descent path wasn't shifting with the rail angle -- was evaluating the shift per-point along the descent instead of once, at apogee**
- Reported directly: "landing points are not shifting when the rail angle changes [in 3D]... descent is apogee-based, not rail-based." Root cause: `descent3d.js`'s `toScreen()` called `railShiftFt(zFt)` using each point's OWN current altitude along the path -- since the shift magnitude is `altitude * tan(angle)`, this meant the shift shrank toward `{0,0}` as a point's altitude fell toward the ground during descent, so the landing point (`alt_ft` &asymp; 0) barely moved at all while points nearer apogee visibly did. Physically backwards: the rail-angle deviation accumulates during boost and finishes at burnout/apogee -- everything from apogee down to the ground is a rigid wind-drift descent starting from that one already-offset point, not something that keeps scaling with the rocket's current height on the way down. - Fixed by computing the rail shift ONCE per `path3dDrawScene()` call, from the path's own apogee altitude (`railShiftFt(altFt)`, matching the 2D map's own treatment exactly), instead of re-deriving it per point. - Real design flaw fixed: cell color used to be binned by quartile of whatever distances happened to be in that one table, so the same color meant wildly different things launch to launch (a 188ft miss read as the worst color at a calm, low-altitude site while 337ft read as the best color at a windier one, since each table was only ever graded against itself). Now graded against how far the wind actually carried the rocket that day: a miss under 200ft is always green regardless of that day's drift distance (a floor -- nobody's actually unhappy with a miss that small, and grading it as a percentage of a very small actual drift blows up meaninglessly), and beyond that it's a percentage of the actual drift (25/50/100% cutoffs, placeholders -- not a principled derivation, expect to revisit as more real launches accumulate).
- Added a color legend above the table (`buildAccuracyLegend()`) generated from the same constants the coloring logic itself uses, not hand-duplicated text, so the two can't drift out of sync.

**DARS/Gunter GPS moved to the middle of the field**
- Was the gate coordinate (dars.org's own figure); moved ~2,000ft to the actual setup spot per the user's direct knowledge of the field. The gate location ate nearly the entire pad-drag budget (`MAX_PAD_MOVE_FT`, 2,000ft) on its own, leaving no real room to try a different spot within the field. Maps re-fetched (site.json's bounds/site_px changed with it) and both existing target dates' published zone data regenerated -- the underlying wind captures didn't need re-pulling (drift offsets are wind-only, independent of the pad's absolute position), just re-anchored onto the new center point and new map images.

**Date selector defaults to the upcoming launch; map layer added to permalinks; site-label fix**
- `regenerate_manifest()` now sorts a site's launch dates descending (was ascending) -- the date `<select>` defaults to its first entry, so this is what makes loading a site default to the soonest upcoming launch (or the most recent one, in the gap right after it's passed) instead of the oldest backfilled date. Applied immediately to all 8 sites' existing manifests, not just future pulls.
- Satellite/road map layer is now part of the shareable permalink (`?layer=sat|road`), not just a localStorage preference -- a shared link can force a specific layer regardless of the recipient's own stored choice, useful for a site with no real terrain to avoid where "road" reads much better than satellite.
- Fixed Tripoli Houston South Site's site-picker label reading "Tripoli Houston - Houston South Site" (doubled "Houston" -- the club name and the site's own name both contained it). Site's `name` is now just "South Site".

**Fixed: cron pulls weren't triggering a site redeploy**
- Real bug, caught while checking why a scheduled pull wasn't showing up on the live site: `cron-pulls.yml`'s commits were landing on `master` successfully, but GitHub suppresses `on: push` workflow triggers for pushes made with the default `GITHUB_TOKEN` (an anti-infinite-loop guard) -- so `pages.yml` never redeployed even though the data was really there. Fixed by having each cron job explicitly dispatch `pages.yml` via the API (`gh workflow run`, which isn't subject to that suppression) right after a successful push, but only when something actually changed.
