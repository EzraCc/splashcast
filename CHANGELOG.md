# Changelog

Dated, terse log of notable changes. For the full design rationale and decision history, see [docs/spec.md](docs/spec.md).

## 2026-08-01

**Draggable launch-pad "what-if" position added as a permalink param, encoded as real GPS not a raw ft offset**
- Follow-up to 2026-07-31's permalink audit, which flagged `padOffsetFt` as a real candidate but deliberately held it for a separate pass. Explicit design constraint from direction given this round: encode as GPS coordinates, not the raw ft offset, because this site's own surveyed launch-pad lat/lon has been corrected more than once in this project's history -- an offset alone would silently point at the wrong ground spot if that ever happens again, while a GPS coordinate re-resolves against whatever the current default is.
- `splash_zones.py:build_zone_data()` now publishes `site_lat`/`site_lon` (previously computed server-side only, inside the pre-existing `ft_to_px()` closure, and never exposed to the viewer). Backfilled onto every already-published capture: regenerated the 19 latest-capture JSONs via `splash_zones.py <date> --site <site>` (site_lat/site_lon come from static per-site config, not that day's live pull, so this is safe to do for any already-captured date without touching zone/rain/cloud/temperature data). The 32 older intermediate captures within those same target-date folders (T-2, T-3, etc., not touched by a `run()` call since it only regenerates the latest capture) were patched directly with just the two new fields, sourced from each site's static `maps/<site>/site.json` -- confirmed via diff this touched nothing else in those files. 4 more captures landed mid-session via the regular automated cron pulls (still running the pre-change pipeline) and were regenerated the same way once noticed. All 56 published captures now carry `site_lat`/`site_lon`.
- `app.js`: added `padFtToLatLon()`/`padLatLonToFt()`, mirroring `splash_zones.py`'s existing flat-earth formula (`111320 m/deg lat`, `cos(site_lat)`-scaled for lon, `0.3048` ft-to-m) exactly. `buildPermalinkParams()` writes `pad=<lat>,<lon>` only when the pad has actually moved; read side converts back to ft and applies through the existing `setPadOffsetClamped()`, so a hand-edited or stale URL still respects `MAX_PAD_MOVE_FT` the same as a live drag.
- Verified round-trip with Playwright: a 150ft E / 80ft S drag produces `pad=30.613709,-97.495977` in the URL; loading that URL back resolves to `{x: 149.93, y: -79.98}` ft (float round-trip, not exact 150/-80 -- expected). A pad param corresponding to a 1-degree-lat offset (~365,000 ft) correctly clamps to the site's `MAX_PAD_MOVE_FT` (2000ft) on load, same cap manual dragging respects. Resetting the pad to `{0,0}` removes the `pad` param from the URL rather than leaving a stale `0,0`.

**Rain and thermometer icons added to the two timeline headers**
- `renderRainTimeline()`/`renderTempTimeline()` titles changed to "🌧️ Rain forecast" / "🌡️ Temperature forecast" -- purely cosmetic, no behavior change. Confirmed both render via Playwright's DOM text content (`document.querySelector('.rain-timeline').textContent`); the icons show as placeholder boxes in this session's headless Linux test browser specifically because that environment has no color-emoji font installed, not an app bug -- real browsers on Windows/Mac/mobile/most Linux desktops render these normally.

## 2026-07-31

**Permalink audit: three real gaps closed (model pin, temperature mode, cloud altitude-expand)**
- Audited every interactive control against `buildPermalinkParams()`'s existing list (site/date/mode/layer/hour/deploy/boost/rate/alt/compare/capture). Found three real, same-category gaps: `pinnedModel` (the model-legend pin/isolate, same shape as the already-synced `rate`/`alt`), `tempShowApparent` (this session's new feels-like/actual toggle, never wired up), and `cloudAltitudesExpanded` (the cloud panel's "show all altitudes" expand, a real content-affecting toggle, not just chrome). Added `model`, `temp`, `clouds` params for all three, following the exact existing pattern -- validate against known-good values on read, write only when non-default so an untouched control doesn't clutter every link.
- Deliberately left out: zone/time color pickers (already intentionally `localStorage`, a personal preference rather than shareable "what am I looking at" content), burn-ban dismiss (transient per-session acknowledgment, resets on site/date change already), cloud panel's own collapse/expand (pure visibility chrome, distinct from the altitude-expand toggle above), and map pan/zoom (a continuous 2D+scale state, meaningfully more complex to encode for a feature that already auto-frames sensibly on load).
- Flagged but not implemented: the draggable launch-pad "what-if" position (`padOffsetFt`) is a real candidate, same spirit as the already-synced boost-angle slider, but a 2D coordinate is a bigger encoding decision than the three boolean/enum additions above -- held for a separate pass rather than bundled in silently.
- Verified round-trip both directions for all three: loading a URL with `model=ecmwf&temp=actual&clouds=all` correctly initializes `state.pinnedModel`/`tempShowApparent`/`cloudAltitudesExpanded` (confirmed the UI visually reflects each on load, not just the underlying state), and interacting with each control updates the address bar; returning any of the three to its default value removes that param from the URL again rather than leaving a stale explicit default.

**Temperature toggle: radio-style pair, not a single link naming only the other mode**
- User feedback: the single toggle link only ever showed "Show actual temp" or "Show feels-like temp" -- the CURRENT mode had to be decoded from what the other option's label said, not read directly. Replaced with a `.temp-mode-toggle` two-button pair ("Feels like" / "Actual"), same bordered-pill/active-filled-with-accent visual language as the TIME/View/Deploy toggles in the controls bar, scaled down for this compact header -- both options always labeled, active one highlighted, current state legible at a glance.

**Temperature timeline: actual/feels-like toggle, default feels-like**
- Investigated whether heat index, dew point, or other flyer-relevant fields were available but unused -- none were pulled before this. Confirmed live against the API with real per-model coverage counts (not docs alone) that `apparent_temperature` (Open-Meteo's own combined wind+humidity+temperature "feels like" figure -- covers both heat-index-when-hot and wind-chill-when-cold in one number, not two separate fields) is available with near-full coverage across all 8 live models (HRRR's slightly lower count is just its normal ~48h horizon, not a gap). `dew_point_2m`/`relative_humidity_2m` are also available but not added -- kept this simple per direction: one toggle, not three more timelines.
- `_hourly_variables()` now requests `apparent_temperature` alongside the existing `temperature_2m` (already in every model's base variable list, so this is one more field on requests already being made, not a new pull). `build_temperature_data()`'s cell shape changed from a plain float to `{"actual": .., "apparent": ..}`.
- Viewer: a toggle button in the timeline's own header (same "button names what clicking it does" convention as the cloud panel's "Show all altitudes") switches which figure the bars/axis/tooltip use -- defaults to apparent, since "does this feel dangerous" is closer to what a launch director needs than raw air temperature. Confirmed with real data the two genuinely diverge (Hutto 3pm: 101.7F actual vs 107.7F apparent, a real 6-degree humidity effect) -- not a redundant toggle.
- Real, pre-existing data limitation found while backfilling, not a bug introduced here: `apparent_temperature` is a brand-new field, so already-published *past* target dates can't retroactively get it -- the live endpoint only serves current/future forecasts, and a past-dated target is never re-pulled by the regular cron. Re-pulled the handful of still-upcoming targets (apache_pass/argonia/sd_rocket_jockies/hutto's Aug launches) for real apparent data on the pages most likely to actually be viewed; the remaining, already-past captures gracefully show "no data" for apparent (actual still works everywhere) rather than anything broken. Separately confirmed two of those older captures (hutto 2026-04-04, gunter 2026-07-18) have no `prior_day` temperature data at all in their raw pull, for either actual or apparent -- genuinely missing rows from before those captures were made, not something this change caused.

**Temperature timeline, below the rain one -- same shell, dynamic per-capture scale**
- New `splash_zones.py:build_temperature_data()`, publishing `temperature_2m` data that was already being pulled for every model (used pipeline-side by `window_stats()`'s CLI summary) but never shown in the viewer. Same 11-slot shape as rain (Prior day/Morning + 8am-4pm hourly, restricted to `LIVE_PROFILE_MODELS`), but genuinely simpler: no "chance"-equivalent field, and no confirmed-zero state to special-case -- a temperature reading has no natural zero point the way rain amount or cloud % does, so each cell is just a plain degF float or `None`, not a dict. `prior_day`/`morning` use each window's MAX (peak heat is the more safety-relevant read than an averaged-down number).
- Viewer: considered a fixed bar scale (the same approach rain uses, capped at `RAIN_BAR_MAX_IN`) and rejected it -- confirmed directly that a Hutto April capture (57-75°F) and an August one (76-104°F) have almost no overlap, so any single fixed range would either flatten a mild spring day into a sliver or clip a hot summer one. Scale is instead computed fresh per render from that capture's own real values (padded/rounded to a clean 5° span) and shown as an axis column with just two numbers (min at the bottom, max at the top) -- `position: sticky; left: 0` so it stays visible while the row scrolls horizontally on mobile, rather than scrolling away exactly when comparing a far-right hour against it.
- CSS refactored to share the grid/cell shell between `.rain-*` and `.temp-*` via combined selectors, not two copies -- also sets up cleanly for a possible future move of the cloud panel into this same row.
- Real bug caught and fixed before shipping, introduced in that same refactor: a comment's own prose contained the literal text `.rain-*/.temp-*`, and the `*/` inside it closed the CSS comment early -- everything from there to the next real `*/` got parsed as garbage CSS instead of staying commented out, silently breaking `overflow-x: auto` on *both* timelines (computed style came back `visible`, not `auto`) and leaking the whole page into horizontal scroll on mobile (confirmed: page `scrollWidth` 699 vs a 375px viewport). Fixed by rewording the comment to avoid the character sequence; verified with a brace/comment-balance scan of the whole stylesheet (comments were 40 open / 41 close before the fix, even), then confirmed `overflow-x: auto` actually takes effect and the page returns to 375px scrollWidth.
- Backfilled all 19 currently-published site/target-date combinations, same as the rain rollout.

Verified against real data, light + dark theme: a mixed cell now reads as flat squares sitting under the line for every model reporting zero, with real measurements rising above it -- the "up = positive, down = confirmed zero" split reads correctly at a glance.

**Rain accounting (`pull_live_forecast.py`'s new `rain_stats()`), for a go/no-go call broader than "is it raining on launch day"**
- Four figures per model, all derived from the `precipitation` hourly values every model already pulls (no new API request): `morning_precip` (target date, midnight-8am, before setup), `launch_precip` (`config.RAIN_WINDOW_START/END_HOUR_LOCAL`, 8am-4pm -- a deliberately separate window from the existing `window_stats()`'s wider 8am-5pm `LAUNCH_WINDOW`, which also drives wind/cloud/temp/CAPE stats and `delta_report()`'s day-over-day drift tracking and wasn't touched here), `day_before_precip` (the full calendar day immediately before target date -- a ground-wetness signal independent of whether target date itself sees rain), and `hourly_precip` (one per `SPLASH_HOURS_LOCAL` sample hour -- 9/11/1/3 -- each summing that hour's own bucket plus the one before it, e.g. "9am" = the 8:00 and 9:00 values, read as "around 9am" not "starting at 9am").
- Confirmed live against the real API that none of this needed a wider pull: `past_days=1` (already requested for T-0 captures) returns a complete, non-truncated prior calendar day (verified: exactly 24 hourly rows, not partial), and for T-1..T-7 captures "the day before launch" is always today-or-later relative to the capture, already inside the normal forward forecast horizon. A real multi-day trailing accumulation (considered and rejected first) would have needed actual extra past-day requests; this doesn't.
- Printed as its own block in `summarize()`'s CLI output, separate from the existing per-model wind/cloud/temp/CAPE/window-precip line (which still uses the older, wider window -- kept as-is rather than merged, to avoid changing `delta_report()`'s existing drift comparison). Verified against a real hutto/2026-08-01 capture: each model's four hourly buckets sum to exactly its own `launch_precip` figure (e.g. ECMWF's 0.01+0.00+0.00+0.06 = 0.07in), confirming the bucket boundaries and the window sum agree. Not yet published to the site/viewer -- pipeline-only for now.

## 2026-07-30

**Open-Meteo request timeout cut 30s -> 10s, one more retry, explicit connection cancellation**
- Checked Open-Meteo's actual documented rate limits (their pricing page): 600 calls/min, 5,000/hour, 10,000/day, 300,000/month on the free tier. Our own worst-case usage (~64 requests/run x 4 runs/day) is nowhere close to any of those, so the timeouts investigated below aren't us tripping a quota -- more likely shared free-tier infrastructure slowness on Open-Meteo's side, which client-side pacing can reduce exposure to but not fix at the root.
- Measured real response times directly (32 live requests, mixed sites/models): mean 1.04s, median 1.05s, p90 1.37s, max 2.24s. The old 30s timeout meant a genuinely stuck request sat for a full 30s before giving up, when nothing that's actually going to succeed has ever taken more than ~2.5s. `REQUEST_TIMEOUT_S = 10` (~4x headroom over the slowest real success) plus a 3rd retry attempt (up from 2) -- same total worst-case ceiling as before (30s) but now covers 3 tries instead of waiting out a single 60s two-attempt cycle.
- `fetch_model()`/`fetch_model_at_run()` now open each attempt's request inside a `with requests.Session() as session:` block instead of a bare `requests.get()` -- guarantees the underlying connection is torn down the moment an attempt times out (`Session.__exit__` always runs, even on exception) rather than potentially leaving an abandoned in-flight request for Open-Meteo to keep processing while we've already moved on to a retry. Also added a 1.0s backoff between retry attempts (there was none before -- immediate re-fire at a model that just failed). Verified directly: forced a real timeout (0.001s), confirmed all 3 attempts fire ~1s apart as expected, the exception propagates cleanly, and the process stays fully responsive afterward (no hang, no leaked connection).
