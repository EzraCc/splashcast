# Changelog

Dated, terse log of notable changes. For the full design rationale and decision history, see [docs/spec.md](docs/spec.md).

## 2026-07-30

**Open-Meteo request timeout cut 30s -> 10s, one more retry, explicit connection cancellation**
- Checked Open-Meteo's actual documented rate limits (their pricing page): 600 calls/min, 5,000/hour, 10,000/day, 300,000/month on the free tier. Our own worst-case usage (~64 requests/run x 4 runs/day) is nowhere close to any of those, so the timeouts investigated below aren't us tripping a quota -- more likely shared free-tier infrastructure slowness on Open-Meteo's side, which client-side pacing can reduce exposure to but not fix at the root.
- Measured real response times directly (32 live requests, mixed sites/models): mean 1.04s, median 1.05s, p90 1.37s, max 2.24s. The old 30s timeout meant a genuinely stuck request sat for a full 30s before giving up, when nothing that's actually going to succeed has ever taken more than ~2.5s. `REQUEST_TIMEOUT_S = 10` (~4x headroom over the slowest real success) plus a 3rd retry attempt (up from 2) -- same total worst-case ceiling as before (30s) but now covers 3 tries instead of waiting out a single 60s two-attempt cycle.
- `fetch_model()`/`fetch_model_at_run()` now open each attempt's request inside a `with requests.Session() as session:` block instead of a bare `requests.get()` -- guarantees the underlying connection is torn down the moment an attempt times out (`Session.__exit__` always runs, even on exception) rather than potentially leaving an abandoned in-flight request for Open-Meteo to keep processing while we've already moved on to a retry. Also added a 1.0s backoff between retry attempts (there was none before -- immediate re-fire at a model that just failed). Verified directly: forced a real timeout (0.001s), confirmed all 3 attempts fire ~1s apart as expected, the exception propagates cleanly, and the process stays fully responsive afterward (no hang, no leaked connection).
- Same treatment for `fetch_burn_ban()` (the Texas A&M Forest Service feed) -- a genuinely different host from Open-Meteo, so `REQUEST_TIMEOUT_S`'s own justification didn't transfer, but the same principle did: measured it separately (8 real requests, mean 0.29s, max 0.31s -- faster and tighter than Open-Meteo's own numbers, as expected for a small static text file), landed on `BURN_BAN_TIMEOUT_S = 5` (a wider ~16x margin over the observed max, vs. Open-Meteo's ~4x, given the much smaller sample against a single small government server), 3 attempts, 1.0s backoff, same explicit-`Session` cancellation guarantee.

**Burn-ban check made per-site instead of hardcoded to Williamson County**
- `fetch_burn_ban()` was checking every site's capture (Argonia, Gunter, Seymour, all of them) against Williamson County's status specifically -- correct for Hutto, meaningless for anywhere else, and now that Argonia (KS) and SD Rocket Jockies (SD) actually pull, actively wrong for two more sites on top of that.
- Added `config.BURN_BAN_COUNTY_BY_SITE`, mapping each Texas site to its real county -- verified via FCC's Census Area API (`geo.fcc.gov/api/census/area`) against each site's actual lat/lon rather than guessed from the site name (Apache Pass turned out to be Milam County, Gunter is Grayson, not what their names might suggest). `fetch_burn_ban(county)` now takes the county explicitly instead of reading a single global constant.
- Kansas (Argonia) and South Dakota (SD Rocket Jockies) have no equivalent statewide, machine-readable burn-ban feed -- both states leave burn bans to individual county commissioners with no central aggregator (checked directly: no API/feed found for either state, including third-party aggregators). Those sites are simply absent from `BURN_BAN_COUNTY_BY_SITE`, and `run()` now returns an explicit `{"supported": False}` for them instead of either silently checking the wrong county or reusing a bare `None` (which already meant something different -- "checked, but the request itself failed," status genuinely unknown). `summarize()`/`delta_report()` distinguish all three states now, so a future UI can show no burn-ban status at all for KS/SD rather than a false green or red.
- Confirmed real, live behavior for both Texas and non-Texas sites: Hutto/Apache Pass currently clear, Seymour (Baylor County) currently under a genuine active ban; Argonia and SD Rocket Jockies both correctly report unsupported.

**Live-pull model requests now paced, fixing a real, reproducible per-site cron failure**
- Investigated whether pulling this many sites/models could be hitting rate limits, prompted by a one-off `gfs`/`hrrr` failure on Hutto's Aug 1 pull. Pulled and parsed six days of real GitHub Actions logs (07-19 through 07-25, ~26 runs) for every site in that window -- first pass mis-attributed failures to the wrong site (a log-ordering trap: `pull_live_forecast.py`'s "[site] Pulling live forecast" line only prints *after* that site's own model loop finishes, so a site's own failures appear to precede its own marker line in the raw log). Corrected extraction showed a stark, non-random pattern: `tripoli_houston_south` had zero failures in 21/21 runs (always pulled first each time it shared a run), while `gunter` failed on `gfs`+`hrrr` in 18/18 consecutive runs (always pulled second, immediately after another site's full 8-model burst).
- Root cause: `pull_live_forecast.py`'s `run()` (the actual live-cron path) fired all 8 per-model requests back-to-back with zero pacing -- `fetch_model_at_run()` (the backfill-only path) already had a `_sleep(0.5)` between requests, with a comment noting exactly this failure mode ("observed transient 502s hammering this endpoint back-to-back with no pause"), but that fix was never carried over to the live path. Made worse by `gfs`/`hrrr`/`nam`/`nbm` all sharing one literal endpoint (`api.open-meteo.com/v1/gfs`) -- four requests to the same URL with no delay, repeated for every site in a run.
- Fixed both levels: `run()` now paces its 8 per-model requests (mirroring the backfill path exactly), and `launch_schedule.py`'s `run_pulls_for()`/`run_live_pulls()` now pace between *sites* too (threaded across target-date groups via a new `pause_before_first` param), addressing gunter's specific always-2nd pattern directly. Both skip the pacing under `--dry-run`, so dry-run stays instant.

**Legal disclaimer added to the top of the viewer**
- New `.legal-disclaimer` banner in `site/index.html` (above the `<h1>`), styled via a new rule in `site/assets/css/app.css` matching the app's existing design-token system rather than inventing new colors. States the tool is a planning aid, not legal advice, and names both burn-ban status and splash-zone estimates specifically -- the two outputs most likely to get read as authoritative safety/legal guidance rather than informational. Verified rendering in both light and dark theme via a local Playwright screenshot (the app has explicit dark-mode CSS overrides, not just `prefers-color-scheme`).

**Live-pull requests grouped by shared Open-Meteo endpoint; grouped-fetch fallback + a 15-minute "surge" retry**
- `gfs`/`hrrr`/`nam`/`nbm` (all on Open-Meteo's `/v1/gfs` endpoint) are now pulled in one request via a comma-separated `models` param instead of four separate ones -- Open-Meteo suffixes every hourly variable with the model id in a multi-model response; new `fetch_grouped_models()`/`_split_grouped_response()` undo that suffixing back into the same per-model shape `parse_hourly()` already expects. Cuts a site's live pull from 8 requests to 5. Verified against the live API: identical row counts and values to the old one-request-per-model calls, across all 8 models, for a real hutto/2026-08-01 pull. Caught a real bug during that verification -- naively unioning all 4 models' requested variables leaked NBM's height-level wind fields into GFS/HRRR/NAM's data too (the `hourly` param is shared across every model in a grouped request, so Open-Meteo returned real, non-null data for variables those models were never individually asked for) -- fixed by filtering each model's split-out response back down to its own `_hourly_variables()` set before handing it to `parse_hourly()`.
- Trade-off: a group now fails together instead of one model at a time, so `run()` falls back to pulling each model in a failed group individually (the pre-grouping behavior) rather than losing all four to what might be one bad request.
- Any model still missing after that (a group's fallback, or a standalone model like ecmwf/gem) gets one more chance after a real 15-minute wait (`SURGE_RETRY_WAIT_S`) instead of an immediate re-fire into what might be a live surge on Open-Meteo's own side, not our own request pattern (grouping already addressed the self-inflicted back-to-back-hammering case above). Bounded to a single extra pass, not a loop -- the next scheduled cron run is at most 6h away regardless, so this isn't the only chance to recover the data, just a way to close the common case of a surge lasting minutes rather than hours. Every request already had a hard 10s timeout inside an explicit `Session` context manager (from the timeout-cut work above), so nothing can hang indefinitely no matter how retries are layered. Verified the full escalation ladder (grouped failure -> individual fallback -> surge wait -> retry) with a mocked network + mocked sleep: all 8 models ultimately recovered, and total request counts matched the expected math exactly.
- Real-world validation, manually dispatched: hutto's grouped request failed exactly as designed, the individual-pull fallback recovered all 8 models within ~30s; argonia's fallback also failed for GFS specifically, triggering the surge wait, which recovered it. Caught live in the process: the currently-published capture for hutto at the time (from an earlier run, before any of this existed) had GFS present as a key but null in every hour -- confirmed as the original, now-fixed failure mode, not a new bug.

**Surge retry now polls every 60s instead of one blind 15-minute wait**
- Confirmed sites are pulled strictly sequentially, not in parallel -- `run_pulls_for()` in `launch_schedule.py` calls `pull_live_forecast.py` once per site via a blocking `subprocess.run()`, no threading/asyncio anywhere in the loop. Real parallelism would only load Open-Meteo's shared endpoint harder (the exact thing grouping above was for), so this is intentional, not a gap -- but it does mean one site's retry wait fully blocks whichever site is queued after it in the same run, which the single 15-minute wait above made expensive: a real dispatch (see above) took ~18 minutes total because argonia's wait stacked *after* hutto had already finished.
- `SURGE_RETRY_WAIT_S` (one 900s sleep, retry once) replaced with `SURGE_RETRY_POLL_S`/`SURGE_RETRY_MAX_WAIT_S` (poll every 60s, same 900s ceiling) -- recovers as soon as a transient surge actually clears instead of always paying the full 15min regardless. Verified with a mocked network: a failure that clears within ~60s now only costs one poll (not 15 minutes), and a persistent failure still stops cleanly at exactly 15 polls / 900s and gives up gracefully, same as before.

**Cloud panel: dropped the redundant model-color legend, hover tooltip redesigned, "% covered" label added**
- Removed the cloud panel's own model-color swatch legend (`.cloud-model-legend`) -- duplicated the same model→color mapping already shown in the main "Model" legend in the side column.
- Cloud-cell hover tooltip changed from one row per model (each with its own divider, a long list for 6 models) to a 2-column grid (model name left, `%` right-aligned) -- faster to scan than a tall stack of "Model 42%" lines.
- Added a "% covered" corner label above the Low/Mid/High rows -- the grid's own cell values (e.g. "0-24%") never stated the unit on their own.
- The tooltip's "≥50%: HRRR, ECMWF, ..." name-list in the footer was dropped in favor of bolding each model's own `%` value in place when it's at/above the nogo threshold -- same information, without repeating names already visible in the grid above. The footer's warning badge (⚠) now reuses the exact same `isCloudHot()` flag the at-rest cell's own badge uses (majority of reporting models ≥50%), not a separately-derived rule, so hover and non-hover states can't disagree. Verified against real data: a majority-hot cell bolds the qualifying models and shows the badge; a cell with some but not a majority of models ≥50% still bolds those values individually without showing the badge.

## 2026-07-29

**Launch calendar moved to JSON + one-off cancel/move/add/flag overrides**
- `pipeline/launch_schedule.py` hardcoded every club's recurring schedule as Python functions, with no way to represent a one-off exception (cancelled date, moved site, extra ad-hoc date) without hand-editing code. New `pipeline/launch_calendar.json` holds both the recurring rules (4 parameterized shapes: `nth_weekday_monthly`, `holiday_relative_multiday`, `seasonal_site_swap`, `hand_entered`, matching the four kinds already documented in the old file) and one-off `overrides` (matched by `(date, site_id)`, not club/label text, which can get restyled without meaning anything changed); `launch_schedule.py` is now a generic interpreter for that file rather than one hardcoded function per club. `cancel`/`move`'s "from" side and `flag` hard-fail (raise) if they don't match an actual generated event for that year -- a typo'd override silently no-op'ing (still polling a "cancelled" launch, or never polling a "moved" one's new site) is exactly the bug class this exists to prevent. Real overrides entered: AARG's Aug 1 moved Apache Pass -> Hutto (field plowed), a tentative extra AARG Aug 15 date (unconfirmed), a tentative flag on AARG's Sept 5 (may move for Airfest, undecided as of this writing -- both grow-season/off-season-overlap sites flagged, not just one), and DARS's July 25 Gunter launch cancelled outright (heat).
- New CLI flags (`--cancel`/`--move`/`--add`/`--flag`) append correctly-shaped overrides to the JSON file directly, validating the target date/site against the recurring schedule before writing (refuses instead of silently writing a no-op override) and auto-filling the club from `config.SITES`.
- Verified the refactor doesn't silently change any existing site's schedule: diffed the new system's recurring-only output (overrides excluded -- they're supposed to diverge) against the old hardcoded output for 2026 *and* 2027, exact match both years (82 and 65 events), before trusting it. `run_live_pulls()`/`run_actual_pulls()`/`events_by_lead()`/`run_pulls_for()` needed zero changes -- confirmed a moved/cancelled launch's cron pulls redirect/stop automatically, since those functions only ever consumed `all_events()`'s `event_date`/`site_id`/`label`.

## 2026-07-28

**Real-flight "delta from predicted landing" percentage was scored against the wrong distance**
- `self_simulated_boost_adjusted`'s error is purely a descent-model error (real measured apogee + simulated descent vs. real landing -- apogee's real GPS offset from the pad cancels out of that difference exactly, since it's measured, not predicted, and this sim only ever models apogee-to-ground), but its percentage was being scaled against pad-to-landing distance, which is dominated by real boost-phase/weathercocking drift the sim never touches or tries to explain. A flight with real boost drift that happened to partly cancel with its descent drift (net pad-to-landing small) scored an inflated, misleading percentage under the old basis -- confirmed exactly this on Tripoli Houston South's J435 flight: 75.2% "of actual drift" drops to a much more honest 47.2% once scaled against the real apogee-to-landing descent distance instead (same 414.4ft absolute error either way). New `pct_of_descent_drift` key (rather than silently redefining what the shared `pct_of_actual_drift` key means depending on which field it's attached to); `self_simulated_descent_only` and `compare_to_pipeline()`'s other-model comparisons are unchanged -- different questions, where the old pad-relative framing still holds. Regenerated/patched the three already-published GPS-tracked real flights (two Tripoli Houston South, one Hearne) to reflect the fix.

**GitHub Pages asset versioning + auto-reload on stale mobile tabs**
- GitHub Pages sends identical `Cache-Control: max-age=600` on every file regardless of type (no per-path header control the way Netlify/Cloudflare Pages' `_headers` allows) -- short enough that a real reload already picks up a new deploy, but a mobile browser reopening a backgrounded tab (or a home-screen-added icon) routinely serves everything, index.html included, straight from disk/bfcache without ever touching the network, no matter how short `max-age` is. `pages.yml` now stamps `app.js`/`app.css`'s URLs in `index.html` with the deploying commit's SHA (`?v=<sha>`) and writes a small `version.json`, right before the existing `upload-pages-artifact` step -- a deploy-time-only rewrite, nothing committed to the repo carries it. `app.js` reads its own `?v=` off `document.currentScript.src`, and on `visibilitychange`-to-visible or a bfcache `pageshow` (`evt.persisted`), fetches `version.json` (cache-busting query + `cache: 'no-store'`) and reloads if it's stale -- only ever fires at the moment a hidden tab becomes visible again, never mid-interaction. Verified end-to-end against a local deploy simulation and live on the deployed site.

**Info button explaining how real-flight numbers are calculated**
- New generic info button (matching the existing legend `.info-btn` hover/click-to-reveal pattern) on the real-flight legend row. Explains launch/apogee/landing/predicted-landing generically -- what's real GPS vs. estimated, and specifically that predicted landing is based on apogee (real or estimated), not the launch/rail position, since that's the exact point of confusion that led to the percentage-basis fix above. Flight-specific notes (a no-GPS flight's own estimation caveat) deliberately stay in that flight's own info box, not duplicated into this generic hint.

**Seymour and Argonia's map imagery was well below every other site's zoom level**
- `pick_zoom()` was purely tile-budget-driven (350 tiles), with no floor -- Seymour (45,000ft waiver) and Argonia (50,000ft waiver) have detail boxes scaled ~4.5-5x Hutto's linear size, so they fell to zoom 15/14 respectively instead of 16 (each zoom step halves ground distance/pixel, so 2x/4x blurrier per pixel than zoom 16). New `min_zoom` param on `pick_zoom()`, `MIN_DETAIL_ZOOM = 16` applied to the detail crop specifically (not the wide contextual one, which has no such floor). Re-fetched both sites' detail imagery at zoom 16 (~1,150-1,520 tiles each; patched 2 tiles that failed transiently in Argonia's road layer directly into the raw PNG rather than re-fetching all 1,521 again) and regenerated every already-published target date for both sites, since the new `image_size_px` was baked into each one's `image_view_box`/`ft_to_px_scale`.

## 2026-07-21

**Real-flight comparison now works for altimeters with no GPS at all (`analyze_no_gps()`, `load_blueraven_lr_csv()`)**
- First non-GPS flight: Apache Pass, 2026-07-04 (BlueRaven SN0829, "Konrad" on TRF) -- a barometer-only altimeter with onboard inertial (accelerometer/gyro) position estimates but no GPS receiver. Real apogee altitude and real ground-equivalent descent rates are still fully recoverable from the barometer alone (same methodology as the GPS-tracked path), but boost-phase drift can't be *measured* without a real apogee GPS fix -- only *estimated*, by assuming the descent-only wind simulation is accurate and backing the boost-phase offset out of the difference between that simulation and a real hand-recorded landing GPS pin (valid because the wind model is ~translation-invariant -- it varies by altitude, not horizontal position; algebraically this already incorporates the real hand-recorded launch-rail GPS too, even though that pin never appears explicitly in the formula -- see `analyze_no_gps()`'s own comments). That estimate is clearly flagged end to end (`apogee.position_source`/`position_estimation_note` in the summary JSON, a dedicated note in the viewer's info box) and never scored as if it were a measurement: `predicted_landing_offset_from_pad_ft` is that same estimated apogee run back through the same descent sim, which lands exactly on the real recorded landing point by construction -- a self-consistency check on the reconstructed flight (rail -> estimated apogee -> real wind descent -> landing), not an independent prediction, so there's no self-simulated accuracy figure in `delta_from_predictions` for this kind of flight (publishing one would just report back the zero it was solved to produce). The T-0 model-forecast comparisons remain fully independent and are the only real scoring available for a flight like this.
- BlueRaven's own onboard `Inertial_Altitude`/`Inertial_DR_Position`/`Inertial_CR_position` (and, it turns out, `Velocity_Up` -- and by extension the firmware's own summary-reported descent rates) went unusable on this flight: confirmed directly against the raw 500Hz gyro data that the rocket's rotation rate briefly exceeded the sensor's own +-2000 deg/sec measurement ceiling right at apogee coast (peak 2,315 deg/sec, this rocket's unusually high roll rate -- 1,880 deg/sec at burnout -- leaves little headroom), which BlueRaven's own manual documents as a "loses track of which way is up" failure mode. `load_blueraven_lr_csv()` relies on the barometer throughout instead, same as every other tracker format here already does for altitude.
- `load_blueraven_lr_csv()` decimates the LR export (50Hz on this flight) to ~1 sample/sec before handing it to the shared core -- `find_main_deploy_index()`'s windowing is tuned against the Deluxe tracker's own roughly-1Hz cadence, and running it undecimated false-triggered a "main deploy" a fraction of a second after apogee (right in the same noisy near-zero-airspeed window) instead of the real one two minutes later.
- History mode's real-flight marker now shows a fourth element on hover/click -- this flight's own apogee (lime-green triangle), real for a GPS-tracked flight or estimated (see above) for a no-GPS one, either way positioned via the same `apogee.offset_from_pad_ft` field the map already uses for the rail/landing/predicted-landing markers.
- The info box's "apogee" line now also shows distance from pad and angle off vertical, e.g. "apogee 10,476.4 ft (368 ft from pad, 2.0&deg; off vertical)" -- both recomputed live against the pad's current (possibly dragged) position, same as the existing "landing ... ft from pad" line, so the angle reads correctly relative to wherever the pad actually is once a click has snapped it to a flight's real rail.

## 2026-07-20

**Real GPS-flight-vs-prediction comparison (`pipeline/analyze_real_flight.py`)**
- New reusable capability: given a real GPS-tracked flight, derives apogee, drogue/main descent rates (ground-density-equivalent, so they're comparable to the configured rate constants), and landing point directly from the track, then scores it against everything already published for that site/date -- a self-simulation using the real apogee + real rates + a real HRRR-analysis wind profile interpolated to the actual launch time, every model's own same-day (T-0) forecast, the HRRR-analysis "actual" proxy (flagged as retrospective-only -- it isn't available until the day after, so it was never a real-time predictor), and whether the real landing point falls inside the published core hull.
- First real flight run through it (Hearne, 2026-07-11): boost-phase drift (measured directly from the real apogee's GPS offset from the pad, not modeled/assumed) turned out to matter a lot -- folding it in dropped the self-simulation's error from 501ft to 207ft. Real landing fell outside the published splash zone both hours checked. Real descent rates (drogue ~60fps, main ~27fps) diverged from the configured dual-deploy constants (80/100 and 10/20fps) in opposite directions -- one flight, not enough to recalibrate anything, but a real data point.
- Deliberately split in two: the comparison logic above is source-format-agnostic; parsing a specific tracker's raw export into the plain sample list it consumes is not, and stays isolated in its own small loader function (see the module's own docstring) since raw formats vary and aren't standardized yet. Raw tracker logs themselves are gitignored (`pipeline/data/actuals/`) -- only the derived summary JSON gets published, now under `site/data/<site_id>/real_flights/` (the servable tree, not a pipeline-internal one) so the viewer can fetch it directly.
- Every delta now carries a `pct_of_actual_drift` alongside its raw feet figure, same reasoning as the History accuracy table's redesign a few days back -- 500ft is a very different miss at a 3,500ft actual drift than at a 500ft one.
- Also now derives: real launch (liftoff) time, separate from apogee time -- approximated as the last sample still near the ground baseline before a sustained climb, since trackers often lose/degrade their fix in the first instant of motion; and the real boost-phase angle off vertical, measured directly from the GPS offset between the pad and apogee, as a sanity check against `config.BOOST_ANGLE_OFF_VERTICAL_DEG` (the assumed buffer angle) -- 2.0&deg; measured vs. 10&deg; assumed for the first flight run through it, comfortably inside the buffer.
- History mode now plots a real flight (when one exists for the current site/target date) as its own marker -- distinct shape/color from every model and from the "actual" star. Hover for a quick look; click pins the info box open (click anywhere else to close), since touch has no hover state to fall back on and needed a full substitute, not just a shortcut.
- Fixed: the real-flight markers (this flight's real launch rail, its own predicted landing, and its real landing point) are genuine GPS-measured positions -- they were incorrectly shifting along with the map's separate, pre-existing draggable "pad" crosshair (a "what if the pad were here" exploration tool that's meant to move every *model* point and the splash-zone hull, not real GPS fixes). They now stay fixed on screen regardless of where that pad marker's been dragged.
- Clicking the real-flight marker also snaps that pad crosshair to this flight's real launch-rail GPS offset, so the model/splash-zone projections line up against where the rocket actually flew without the user needing to find and drag the crosshair by hand -- the info box's "landing N ft from pad" figure is computed live off wherever the pad currently sits, so it reads as the flight's true drift distance once snapped. Closing the box normally (re-clicking the marker, or clicking elsewhere) restores the pad to wherever it was *before* the snap, rather than stranding it at the rail; dragging the pad by hand, or hitting its own Reset button, while a flight's pinned closes the comparison instead (the numbers would no longer describe where the pad actually is) but leaves the pad exactly where that drag/reset put it -- the user's own placement isn't something to revert.

**History mode's altitude/forecast-age, and the boost-angle slider, are now permalink params too**
- History mode's altitude selection (`compare`, shared with "By time of day" -- both use the same "which altitude to compare across hours" field) and its "Forecast age" selection (new `capture` param, the pinned capture date) now round-trip through the URL like every other durable "what am I looking at" choice, so a shared History-mode link reproduces the same altitude/forecast-age a viewer had pinned instead of always landing on the defaults.
